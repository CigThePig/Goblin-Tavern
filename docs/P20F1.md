# P20F1 — `response_impact` 28 / 70 — Cause Investigation

> Investigated: 2026-05-13 · seed `phase-20-test-seed`, 14-day default pipeline · Vitest 1.6.1 / Node 22

## TL;DR

The `response_impact` gate scores the **mean of `consequenceProfile.impactScore`** across every seed generated during a 14-day run. Today that mean is **28**, the threshold is **70**, gap **−42**.

The mean of 28 is **not** a scorer bug nor a defaulting bug — the formula is doing exactly what it claims to do. The 28 falls out of two compounding facts:

1. **The catalog is structurally light.** The average consequence profile carries only **1.77 immediate effects + 0.66 delayed effects + 1.00 memory + 0.31 future hook**. With those counts, the formula is mathematically unable to produce a number much above ~30 for the average, even when amounts are healthy.
2. **The scorer is missing two of the four design dimensions.** The Phase 19 design doc (`phases-16-20.md:1936-1946`) calls for breadth (cross-system reach), permanence, actor-relationship changes, and reputation effects to feed the score. The implementation only counts `kindWeight × |amount|` plus flat per-memory and per-future-hook bonuses. There is no breadth multiplier, no permanence factor, no relationship/reputation axis.

The threshold itself is also questionable: 70 is the `MONTHLY` strategic-tier classification (`impactScoring.ts:78-83`). Asking for the *average* profile to land at the strategic tier is asking for every "ignore", "comfort staff", and "discount" response to score like a months-spanning campaign decision.

Verdict: **content gap + scorer gap + threshold gap**, in that order of impact. Not a check bug.

---

## 1. What the gate measures

`src/sim/testing/readinessReport.ts:183-209` — `scoreResponseImpact`:

```ts
for every seed in seedsToday across the run:
  for every profile in seed.consequenceProfiles:
    total += profile.impactScore
    count += 1
score = round(total / count)
```

Pure mean. No filtering, no weighting, no bucketing. Whatever the resolver writes onto `consequenceProfile.impactScore`, that integer is what gets averaged. The gate cannot fail in isolation — its score is fully determined by what the seed generators emit.

Threshold: `READINESS_THRESHOLDS.response_impact = 70` (`readinessReport.ts:54`).

## 2. What the score formula actually does

`src/sim/modules/issues/impactScoring.ts:33-52` — `scoreEffects`:

```ts
const STATE_CHANGE_WEIGHT = 1.0
const PRESSURE_WEIGHT     = 0.8
const CAUSE_WEIGHT        = 0.6
const MEMORY_WEIGHT       = 0.4
const FUTURE_HOOK_WEIGHT  = 0.5

total = 0
for each immediate effect e:
  total += weightFor(e.kind) * |e.amount ?? 5|
for each delayed effect e:
  total += weightFor(e.kind) * |e.amount ?? 5| * 0.7
total += MEMORY_WEIGHT * 8 * memoriesCount        // = 3.2 per memory
total += FUTURE_HOOK_WEIGHT * 10 * futureHooksCount  // = 5  per hook
clamp 0..100
```

`makeProfile` in `generatorHelpers.ts:62-67` calls `scoreProfile`, which calls `scoreEffects` with the four arrays. So every profile gets its score the same way at construction time.

**Important nuance:** the `?? 5` defaults apply only when `amount` is `undefined`/`null`. If a generator writes `amount: 0` (which several do for `cause` / `future_hook` previews), the magnitude is **0**, contributing nothing. I verified this is *not* causing today's failure (see §3) but it's a footgun if future authors lean on it.

### What the formula does *not* do

The Phase 19 design (`phases-16-20.md:1936-1946`) lists seven dimensions the impact score should consider:

| Design dimension | Implemented? |
|---|---|
| visible state changes | ✅ via `state_change` weight |
| pressure changes | ✅ via `pressure` weight |
| memory importance | ⚠️ flat bonus, no per-memory strength |
| future hook strength | ⚠️ flat bonus, no per-hook strength |
| actor relationship changes | ❌ no axis |
| reputation effects | ❌ no axis |
| resource cost/gain | ⚠️ rolled into `state_change` magnitude only |

Plus the design verbiage in `phases-16-20.md` mentions **breadth** (touches multiple systems) and **permanence** (long-lived changes count more); neither is in the formula. A profile that sets one stat by 30 and a profile that sets three different stats by 10 each get the same total — no breadth multiplier.

### Per-profile component counts

| Component | Mean per profile |
|---|---:|

This is the structural ceiling. With ~1.77 immediate effects averaging |amount| ≈ 12.5, kind-weight ≈ 0.85, you get ~19. Add ~0.6 delayed effects × 0.7 multiplier ≈ 2. Add 1 memory × 3.2 + 0.31 hook × 5 = 4.75. **Predicted average ≈ 26–28** — exactly what the diagnostic prints. The formula is doing what it says; the catalog just doesn't give it more to work with.

### Why amounts aren't the problem

I expected `amount: 0` previews to be deflating the score. They aren't:

```
zeroAmountEffects:    0  / 872 immediate effects
nonZeroAmountEffects: 872
undefAmountEffects:   0
```

Authors are uniformly passing real magnitudes for immediate effects. The deflation comes from the *count* of effects per profile, not their per-effect magnitude.

## 4. Root cause — three contributing factors

### 4.1 The catalog is content-light (largest contributor)

Most consequence profiles describe a small ack-tier outcome: shift one stat, drop a memory marker, done. This is what the Phase 19 sample-content boilerplate looks like:

```ts
makeProfile({
  id: 'comfort_staff_profile',
  immediateEffects: [
    effect('state_change', `staff.${chosen.id}.loyalty`, 10, ...),
    effect('state_change', `staff.${chosen.id}.stress`, -8, ...),
  ],
  delayedEffects: [],
  memories: [{ id: `staff_comforted_${chosen.id}`, ... }],
  futureHooks: [],
})
```

Two effects, one memory, no follow-on. The doc target was four-dimensional outcomes that *also* touch reputation, faction, supplier, downstream future hooks etc. The catalog as committed reads as a first-pass scaffold, not a tuned response set.

### 4.2 The scorer is missing design dimensions

Even if the catalog were richer, the scorer would still under-credit it because it has no axis for:

- **Breadth.** Profile A: `state_change=20` on one path. Profile B: `state_change=10` on three different paths. Same total = 20 in both. Phase 19 doc explicitly says breadth should weigh more.
- **Permanence.** A pressure shift that decays in two days should score lower than a `state.causes` entry that persists; the formula gives them comparable credit.
- **Actor / relationship changes.** No `relationship` effect kind exists; everything must be expressed as a `state_change` against a generic path.
- **Reputation effects.** Same — folded into `state_change` so the scorer can't recognise it as its own dimension.
- **Memory strength.** Every memory is worth a flat `0.4 × 8 = 3.2`. The Phase 18 memory module supports per-memory strength; the scorer ignores it.
- **Future hook strength.** Same flat-rate problem.

This is why even strong profiles like `restock_profile` need a `state_change` of magnitude 60 to clear the threshold — there is no other lever the author can pull.

### 4.3 The threshold is calibrated to a single-profile classification, not an average

`impactScoring.ts:78-83`:

```ts
IMPACT_THRESHOLDS = { MINOR: 15, NORMAL: 30, MAJOR: 60, MONTHLY: 70 }
```

`MONTHLY = 70` is the boundary between `major` and `strategic` classifications. The gate threshold is **also 70**, applied to the *mean of every profile*. Reading those side-by-side: the gate is asking that the *average* response in the catalog be classified `strategic`. By construction the catalog must contain weak ("ignore") and strong ("hire security") responses, so a healthy average should land somewhere in `normal` (30–60), not `strategic` (≥70).

The plan doc (`phases-16-20.md:2558`) actually wants this stricter still — `Response Impact >= 75`. With the current shape of profiles, that bar is mathematically out of reach.

## 5. Where the bug lives (file-level pointers)

For each subroot of the failure, the file ranges to look at when fixing:

- **Catalog content gap** — `src/sim/modules/issues/issueSeedGenerators.ts` and `src/sim/modules/issues/expandedSeedGenerators.ts`. Every `makeProfile({...})` call site. The lowest-scoring families to look at first:
  - `supplier_relationship` (avg 13.2) — lots of `cause` effects with small `amount`, no delayed knock-ons.
  - `staff_identity` (avg 18.2) — most profiles have one to two `state_change`s and nothing else; no faction/reputation breadth.
  - `customer_complaint` (avg 25.0) — coin/satisfaction trade and stop.
- **Scorer gap** — `src/sim/modules/issues/impactScoring.ts`. The whole file is ~95 lines; missing axes (breadth, permanence, relationship, reputation) need to be added explicitly. `scoreEffects` is the function to extend.
- **Threshold drift** — `src/sim/testing/readinessReport.ts:54` (`response_impact: 70`) vs `docs/plans/phases-16-20.md:2558` (`75`). Reconcile after the formula changes, or accept that `70` is a soft target tracking design intent, not a hard arithmetic ceiling.
- **Resolver-side scoring** — `src/sim/modules/responses/responseResolver.ts:335` calls `scoreAppliedEffects(applied)` from `impactScoring.ts:67-75`. Note that this is a **separate** scoring path used at apply-time, not for `consequenceProfile.impactScore`. Any formula change has to be made consistently in both `scoreEffects` and `scoreAppliedEffects` or the gate score and the report will diverge.

## 6. Why it's not the check that's broken

Three reasons the scorer gate is doing its job correctly:

1. The gate's reported `28` is reproducible to four decimals (`28.12348…`) when I sum the same 494 profiles by hand from the same seed.
2. Every individual `impactScore` reproduces from the published `scoreEffects` formula. No silent clamping below the mean, no off-by-one in `Math.round`.
3. The gate doesn't filter or down-weight; it's a literal arithmetic mean. The only way to move it is to change either the formula (`impactScoring.ts`) or the catalog (`issueSeedGenerators.ts` / `expandedSeedGenerators.ts`) or both.

This rules out "the scorer is wrong". The scorer's claim — "average consequence profile impact: 28" — is true.

## 7. Suggested order of operations to fix

(Not asked for, but small enough to leave for whoever picks this up.)

1. **Tune the formula first.** Add a breadth multiplier (count of distinct `target` prefixes touched) and lift `memoryCount`/`futureHooksCount` from flat coefficients to `Σ strength`. Both are local edits in `impactScoring.ts`. Re-run the gate; it should move into the 35–45 range without any catalog changes.
2. **Audit lowest families.** Walk `supplier_relationship` and `staff_identity` profiles and add the second-order effects that the Phase 19 doc anticipates (cross-faction reputation pings, supplier morale pressures, future-hook chains). Each family should average ≥ NORMAL (30).
3. **Then re-decide the threshold.** Once the formula is correct and the catalog is no longer content-light, set the threshold to whatever `mean(major + minor + normal)` actually lands at — likely 45–55, not 70. Update both `readinessReport.ts:54` and `phases-16-20.md:2558` together.

P40 §7 (`social_consequence_quality`) will move with this fix because its impactAxis is the same `impactScore` averaged over expanded-family profiles only — see `expandedReadinessReport.ts:849`.
